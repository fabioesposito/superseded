# Alembic Migrations Design

**Date:** 2026-07-07
**Status:** Approved
**Approach:** SQLAlchemy models as source of truth + Alembic autogenerate, async env.py

## Overview

Replace the two parallel, hand-maintained `SCHEMA` constants in
`memory/store.py` (SQLite) and `memory/postgres.py` (Postgres) with a single
source of truth: SQLAlchemy declarative models. Alembic generates and runs
versioned migrations against both backends. The existing async query layer
(`aiosqlite` / `asyncpg`) and the `Store` Protocol are unchanged — only schema
creation, schema evolution, and the `open()`/`init()` entrypoints move to
Alembic.

The driving problem is schema drift. The two constants have already diverged in
subtle ways (e.g. SQLite `findings.comment_id INTEGER` vs Postgres `BIGINT`;
`installation_config` carries an `ON DELETE CASCADE` foreign key on SQLite but
not on Postgres), and `PostgresStore` has no schema-evolution story at all
(only idempotent `CREATE TABLE IF NOT EXISTS`, so it cannot add columns to
existing tables). Centralizing on models + Alembic eliminates the drift and
gives both backends real versioned migrations.

## Goals

- One schema definition (SQLAlchemy models) for both SQLite and Postgres.
- Versioned, reviewable migration files generated via `alembic revision
  --autogenerate`.
- Existing pre-Alembic databases adopted transparently (no manual stamp step,
  no data loss).
- Auto-upgrade on every `store.open()` for both backends — the embedded SQLite
  UX ("it just heals on launch") is preserved, and Postgres adopts the same
  model.
- No new database driver dependency (reuse `asyncpg` / `aiosqlite`).
- A test-time guardrail that fails when the models and the head migration
  diverge, so the single-source-of-truth property is maintained going forward.

## Non-Goals

- Rewriting the store query methods on top of SQLAlchemy. Raw SQL queries in
  `MemoryStore` and `PostgresStore` stay as-is; only schema DDL moves to
  Alembic.
- Introducing an ORM access pattern. Models exist for schema definition and
  autogenerate, not for query construction.
- An explicit-migration operational policy. Auto-upgrade runs on every `open()`
  for both backends (a deliberate tradeoff accepted during design).

## Decisions

| Decision | Choice | Rationale |
|---|---|---|
| Source of truth | SQLAlchemy declarative models | Real single source; autogenerate eliminates hand-diffing |
| When migrations run | Auto-upgrade on every `store.open()` for both backends | Preserves embedded SQLite UX; uniform model |
| Pre-Alembic adoption | Auto-stamp on detection (probe `alembic_version` + tables) | Zero-friction for existing users; no manual step |
| Connection model | Async `env.py` + asyncpg / aiosqlite | Reuses existing drivers; no event-loop blocking |
| Schema representation | Models only (query code unchanged) | Smallest blast radius; isolates change to schema/migration code |

## Architecture

### Module Layout

New and changed files under `src/superseded/memory/`:

```
memory/
├── models.py            # NEW — SQLAlchemy declarative models (single source of truth)
├── migrations/          # NEW — ships inside the wheel
│   ├── __init__.py
│   ├── env.py           # async env.py (asyncpg for PG, aiosqlite for SQLite)
│   ├── script.py.mako
│   └── versions/
│       ├── __init__.py
│       ├── 0001_initial_schema.py        # baseline (autogenerated)
│       └── 0002_add_installation_config_fk_postgres.py
├── alembic_runner.py    # NEW — programmatic Config builder + probe + upgrade
├── backend.py           # unchanged (Store Protocol, make_store)
├── store.py             # MemoryStore: SCHEMA + _migrate() DELETED; open() calls runner
├── postgres.py          # PostgresStore: SCHEMA execute DELETED; open() calls runner
└── _stats_sql.py        # unchanged
```

A repo-root `alembic.ini` exists for dev ergonomics only — it lets developers
run `uv run alembic upgrade head` and `uv run alembic revision --autogenerate`
directly. The runtime path never reads `alembic.ini`: `alembic_runner` builds
the Alembic `Config` object programmatically and resolves `script_location`
through `importlib.resources.files("superseded.memory.migrations")`, so the
runner works from an installed wheel.

### Integration Flow on `store.open()`

Both `MemoryStore.open()` and `PostgresStore.open()` follow the same shape:

```
store.open():
    1. Establish own async connection as today
       (aiosqlite file conn / asyncpg pool).
    2. needs_stamp, is_fresh = await _probe()   # uses the store's own async conn
         - check alembic_version table + findings table existence
         - alembic_version absent AND findings present  => pre-Alembic DB => stamp
         - alembic_version absent AND findings absent    => fresh DB       => migrate from zero
         - alembic_version present                        => normal upgrade
    3. await asyncio.to_thread(
           alembic_runner.upgrade_sync,
           db_url, stamp_first=needs_stamp
       )
         - runs in a worker thread so env.py's asyncio.run() does not collide
           with the already-running application event loop
         - runner builds the Config, calls command.stamp() (if requested)
           then command.upgrade("head")
         - env.py spins its own transient async engine for the DDL, separate
           from the store's query connection
```

The probe rides the store's existing async connection via a backend-specific
one-liner (`sqlite_master` for SQLite, `to_regclass` for Postgres), so no
second driver is needed merely to peek at schema state. Alembic's async
`env.py` then opens its own transient engine for the actual DDL — acceptable
for both backends (SQLite WAL permits the brief second writer; Postgres pool
absorbs it).

### Why a worker thread for the runner

`command.upgrade` / `command.stamp` are synchronous Alembic APIs. The async
`env.py` pattern bridges to async via `asyncio.run(...)` internally.
`asyncio.run` cannot be called from inside an already-running event loop, so
the runner must execute in a separate thread (`asyncio.to_thread`). In that
thread there is no running loop, so env.py's internal `asyncio.run` is valid,
and the application's main event loop stays unblocked while DDL runs.

## Schema Reconciliation

The models become the single source, so the existing drift is reconciled to one
definition. The 8 tables and their reconciled types:

| Table / Column | Drift today | Reconciled decision |
|---|---|---|
| `findings.comment_id` | SQLite `INTEGER` / PG `BIGINT` | `BigInteger` → `BIGINT` on PG, `INTEGER` on SQLite (affinity-equivalent; GitHub comment IDs fit int64) |
| `findings.created_at`, all timestamps | SQLite `TIMESTAMP` / PG `TIMESTAMPTZ` | `DateTime(timezone=True)` + `server_default=func.now()` → `TIMESTAMPTZ` on PG, `TIMESTAMP` on SQLite |
| `findings.dismissed` | both `BOOLEAN` | `Boolean`, `server_default=false()` |
| `feedback.id`, all AUTOINCREMENT/IDENTITY PKs | SQLite `AUTOINCREMENT` / PG `GENERATED BY DEFAULT AS IDENTITY` | `BigInteger, autoincrement=True` (dialect renders identity / AUTOINCREMENT) |
| `installation_config` FK to `installations` | SQLite has `ON DELETE CASCADE`, **PG missing it** | FK present in model — PG gains it; reconciled via `0002` |
| all id/count columns | mixed `INTEGER`/`BIGINT` | `BigInteger` uniformly — no value loss |

### Migration Files

1. **`0001_initial_schema.py`** — autogenerated baseline capturing all 8
   tables in their reconciled form. This is what gets stamped onto pre-Alembic
   DBs and what fresh DBs build from.

2. **`0002_add_installation_config_fk_postgres.py`** — reconciliation step.
   Idempotently adds the missing `installation_config → installations` foreign
   key on Postgres only, guarded so it no-ops if the constraint already exists.
   Pre-existing **SQLite** DBs are left without the FK: SQLite cannot
   `ALTER TABLE ADD CONSTRAINT`, and a table rebuild is disproportionate to the
   value. Embedded SQLite DBs are per-user and low-stakes, and cascade-delete
   of installation config is rarely exercised. *Fresh* SQLite DBs receive the
   FK at baseline creation (the model defines it; `0001` creates it).

### Pre-Alembic DB Adoption

| Backend | Existing schema vs baseline | After stamp + upgrade |
|---|---|---|
| Postgres | Matches baseline except missing `installation_config` FK | `0002` reconciles — clean |
| SQLite | Matches baseline modulo absent FK (accepted) and `comment_id` nominal type (affinity-equivalent) | Stamp to `0001`, `0002` no-ops (PG-only) — clean |

The `comment_id` type divergence and the SQLite FK absence are documented in
the `0001` migration docstring as accepted pre-existing-DB divergences — no
silent surprises, no attempt to "repair" them at upgrade time.

## Dependencies and Packaging

### `pyproject.toml` core deps (additions)

- `sqlalchemy>=2.0` — declarative models + async dialect layer.
- `alembic>=1.13` — migration engine.

No new database driver: `asyncpg` and `aiosqlite` are reused as SQLAlchemy
async dialects (`postgresql+asyncpg`, `sqlite+aiosqlite`).

### Wheel packaging

- `src/superseded/memory/migrations/` and `versions/` each gain an
  `__init__.py` so hatchling reliably ships them in the wheel. The directory is
  under `packages = ["src/superseded"]`, but the `__init__.py` makes collection
  unambiguous and lets `importlib.resources` locate the script dir at runtime.

## CLI Surface

- **New `superseded migrate` subcommand** — calls `alembic_runner.upgrade()`
  against the configured DB and prints the resulting revision. Although
  `open()` auto-upgrades, an explicit command gives ops a deliberate way to
  run or inspect migrations (before a deploy, or to diagnose a stuck
  migration) without invoking a review. Follows the existing click style in
  `cli.py`.
- **Dev workflow** for authoring migrations remains the standard Alembic flow:
  `uv run alembic revision --autogenerate -m "..."` using the repo-root
  `alembic.ini` (which points at the in-package `env.py` and a dev
  SQLite/Postgres URL).
- **`superseded init`** is unchanged — it does not touch the DB.

## What Stays Unchanged

- `backend.py` — `Store` Protocol and `make_store` untouched.
- All store query methods (`record_finding`, `get_learned_rules`,
  `refresh_review_stats`, etc.) — raw SQL stays as-is.
- `_stats_sql.py` shared CASE expression.
- Configuration precedence for `agent` / `model`.

## Testing Strategy

### New: `tests/test_migrations.py` (SQLite, always run)

1. **Fresh DB**: empty file → `open()` produces all 8 tables + `alembic_version`
   at head; round-trip a finding to confirm.
2. **Pre-Alembic adoption**: build a DB with the old hand-written SCHEMA + seed
   data, no `alembic_version` → `open()` stamps baseline, upgrades, **seed data
   survives** (the critical regression).
3. **Idempotent re-open**: call `open()` twice → second is a no-op (probe finds
   `alembic_version` at head, skips).
4. **Probe unit tests**: each branch of the `alembic_version × findings`
   existence matrix returns the right `needs_stamp` / `is_fresh` flag.

### Postgres mirrors (`tests/test_postgres_store.py` style)

Same four scenarios under `@pytest.mark.postgres`, skipped unless
`SUPERSEDED_POSTGRES_TEST_DSN` is set (consistent with existing
`addopts = "-m 'not postgres'"`).

### Single-source-of-truth guardrail (key new test)

A test that invokes Alembic's `check` (programmatic equivalent of
`alembic check`) comparing the models to the head revision. **Fails if someone
edits the models without regenerating a migration.** Without this, the drift
problem the design set out to fix silently returns.

### Regression coverage (already exists, must stay green)

- `tests/test_memory_backend.py`, `tests/test_server_store.py`,
  `tests/test_audit_stats.py`, `tests/test_server_worker.py` all exercise
  `store.init()` / `open()` → they validate the new open() path end-to-end
  with no expected test changes.
- `tests/test_integration.py`'s `MemoryStore`-mock pattern is unaffected
  (mocks at `superseded.cli.MemoryStore`, which is not where the runner lives).

### CLI test

`superseded migrate` invocation test in `tests/test_integration.py`, mirroring
the existing click-runner style.

## Performance

After first run, `open()`'s cost is one probe query plus Alembic's "select
version, compare to head" — negligible. No caching layer is needed.

## Risks and Tradeoffs

- **`asyncio.to_thread` + env.py's `asyncio.run`** — verified compatible (the
  worker thread has no running event loop). Covered by the fresh-DB and
  idempotent-re-open tests, both of which run inside the test's own event loop
  and therefore exercise the real deployment shape.
- **SQLite second connection during migration** — WAL mode allows it; the
  migration connection briefly holds the write lock. Documented, low-risk.
- **Auto-upgrade on every server `open()`** means a webhook handler can trigger
  migration DDL. With auto-stamp this is bounded (one-time for pre-Alembic DBs;
  thereafter a cheap no-op), but it is the deliberate tradeoff accepted in the
  design: uniform zero-friction behavior across both backends, at the cost of
  migration failures becoming runtime failures in the request path. The
  `superseded migrate` command exists in part to let operators pre-run
  migrations ahead of a deploy and avoid that path entirely.
